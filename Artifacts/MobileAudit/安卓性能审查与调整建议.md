# 安卓性能审查与后续四关制作规范

日期：2026-10-19。范围：项目业务脚本、4 个正式场景、预制体、全部现存 27 个动画片段及控制器依赖、823 张 PNG、音视频导入配置、URP 与 Android 设置。第三方示例不按自有玩法逐行评审。检查期间资源目录有外部移动/删除，资源清单已刷新到最新一次快照。

本次只分析并输出报告，未修改游戏脚本、场景、动画或导入参数。没有连接安卓真机运行，以下是静态风险评估，不是实测帧率、包大小或运行内存。GUID 依赖遍历包含隐藏对象与控制器持有的引用；不代表所有对象同时绘制或所有纹理必然同时驻留。

## 结论

有明显的手机加载和内存风险。最高优先级是选关与关卡的资源隔离，以及全高清序列动画。第一关只有两头牛、少量 NPC，并非玩法本身过于复杂；现在可以修正结构，不需要推倒重做。

上表只统计 PNG，排除 JPG、PSD、字体内嵌图、音频、视频解码缓冲及引擎开销；依赖之间会共享，不能把各场景相加作为实际内存。源尺寸未扣除 Max Size 缩放，也没有模拟安卓实际压缩格式、设备兼容回退或图集，因此不是实际内存预测。项目默认压缩设置存在，未发现 PNG 配置专门的 Android override，不代表图片全部未压缩。

## P0：在制作第二关前调整

### 1. 选关不要直接引用完整关卡

Select.unity 的 5 处 HideAndInstantiate 都直接引用 Level1.prefab。HideAndInstantiate.OnAnimationFrame 使用 CanvasGroup.alpha = 0 隐藏宿主 UI，再同步 Instantiate 关卡；没有卸载 Select 场景。UIPageSwitch 也只对页面 SetActive。

后果：从此入口进入第一关时，选关的资源引用仍在；将来每个入口改挂不同关卡预制体，会扩大选关依赖。透明/关闭对象、Destroy 关卡实例都不等同于已经释放所有纹理引用。

建议：Select 只保留关卡 ID、场景名、轻量静态缩略图、锁定状态。点击后使用统一过场与加载界面，LoadSceneAsync 加载对应 Level1～Level5，明确卸载旧场景。只跨场景保留存档、设置、音频等少量服务，不携带完整关卡。已有 Level1.unity 可作为独立关卡入口，不需要从 Select 实例化整关。

注意：仅改 LoadSceneAsync 不会自动消除激活时的所有开销；仍要检查 Awake/Start、UI 构建和纹理上传。异步加载的激活阶段也可能产生短暂停顿。

### 2. 大型序列动画不要全部预挂在选关页面

五组砖画片段共引用约 426 张独立全高清图片；多数片段约 2～3.5 秒。LOGOShow.anim 引用 135 张 1920×1080 图片、时长约 5.5 秒；Logo 目录另有未被此片段引用的帧，目录图片数与动画实际引用数不同。Title 片段引用 12 张全高清图片。

建议：无透明需求的 Logo、全屏过场优先试做 H.264 视频，由 VideoPlayer 硬件解码；设备上验证首帧黑屏、Prepare 完成、音画、切后台恢复、播放结束与失败兜底。小型解锁效果可以只用静帧加淡入/缩放/遮罩。确需透明的帧动画，先减少尺寸与重复帧，再按需加载一组，播完归还引用。

逐帧变化必须保留原有时长和事件：现有事件有 TriggerShowObject、OnAnimationFrame，抽帧、转视频后必须在新流程中接回，避免进关按钮或关卡不出现。Animation Samples=60 不等于每秒存在 60 张不同图片；降低 Samples 不会自动减少所引用图片的数量和占用。不要把所有全高清序列塞进一个巨大图集。

### 3. 第一关玩家控制器只挂实际需要的动作

现有 Player2.controller 除 Idle/Walk/Run，还持有攻击、持剑、拍手、武器等片段；不少状态没有过渡，但仍是资源依赖。保留素材供后续关卡使用，不必把所有动作常挂在第一关控制器上。

建议：建立第一关所需的精简控制器。先核对代码中的 Animator.Play/CrossFade、状态名和动画事件，确认其他动作未使用后解除依赖；后续按关卡配置控制器或 Override Controller。不要直接删除动作源文件。

检查期间跳跃目录被移除，当前控制器的 Jump 状态仍持有 GUID 80718419f8d5c4a4b9b8b3632504b2a7，而扫描未发现对应资源。请在 Unity 检查该状态是否显示 Missing；如果不需要，清掉状态/引用，如果需要则恢复匹配 .meta 的素材。

## P1：建立后续素材的固定规范

| 用途 | 建议起始规格，最终以手机画面为准 |
| --- | --- |
| 角色动作 | 先试 256～512 级别导入尺寸，按屏幕实际角色高度决定；动作可先尝试 12～24 张/秒，快速动作另行保留 |
| 牛、工具、小道具 | 先试 256～512，较大动物/近景可提高；不要让小耙子一直使用近 3K 源尺寸的导入规格 |
| 普通按钮/图标 | 64～256 为起点，大按钮或高密度显示适当提高 |
| 全屏背景 | 先试 1280×720～1920×1080，保留画面需要，不要统一无脑压到 512 |
| 文字/书法与砖画细节 | 单独对比压缩伪影；优先保护可读性 |
| 序列帧 | 根据实际显示区域设上限，并限制总帧数，不按普通静态背景无限堆积 |

以上是测试起点，不是强制统一尺寸。修改 Max Size 通常比直接破坏源图更容易回退。裁透明留白必须保持整套动画一致的画布、pivot、PPU 和位移关系，否则角色会抖动或大小改变。压缩 PNG 文件本身不等于减少 GPU 纹理内存。

安卓纹理：针对目标设备试 ASTC 6×6；有细线/文字的素材可试 ASTC 4×4。如支持更旧设备，规划 ETC2 或纹理格式分发，测试不支持格式时的回退。现有 Read/Write 已关闭、绝大多数未开 Mip Maps，这是适合当前许多 2D 素材的基础，不必盲目改开。不要把低质量全局设置当作解决所有大 Sprite 的办法；无 mipmap 的图片不靠全局 mipmap 限制等比例省内存。

图集：目前没有 Sprite Atlas。优先为小型 UI、同一角色/同关卡的小图分组建图集；避免一个公共图集把 5 关都绑在一起。UI 图集需要注意材质、Canvas、裁剪和同屏顺序，不能保证自动合成一次绘制。LevelBase 的拼图通过 Sprite.Create 读取 restoredBrick 的纹理矩形，给这类图片加入打包旋转/紧密裁剪的图集前要专门验证，不能直接批量套用。

五关制作规则：每关独立 Scene，只有本关 NPC/背景/音乐/动作；公共角色及小 UI 有清晰共享边界。前后关交替访问后内存应回落到稳定基线，允许合理缓存，但不能每次都增长。先使用独立场景管理即可；确有需要再引入 Addressables，使用后匹配 Release/Unload，避免直接引用把按需加载变回全部依赖。

## P1：触屏和界面在第二关前跑通

PlayerMovement 读取 Horizontal/Vertical 与 Shift；NPCInteraction、LevelBase、DialogueManager 使用 E/空格；FarmingPuzzle 使用 R 重置，弹窗支持 Esc。这些入口没有完整的触屏等价实现。

把移动方向、交互、跑步、重置、返回抽成游戏操作方法，由键盘或屏幕按钮调用。不要在每个新关卡复制一套按键判断。移动在 FixedUpdate 使用采集到的输入，按钮的按下事件在 Update/事件回调记录；按需测试移动与操作的多点触控。

LevelBase 运行时新建 Canvas，使用固定 1920×1080 参考尺寸；项目已有 AdaptiveCanvasScaler 和 SafeAreaButton，但生成的这套 LevelCanvas 没有自动应用它们。统一 SafeArea 容器，覆盖顶部提示、拼图入口、返回和对话，适配长屏、挖孔与手势边缘。鼠标 Hover 展示的信息要给手机点击/常显入口。

## P2：代码和绘制开销

1. 音量滑块：IndexMainMenu.onValueChanged 每次变化调用 DataSystem 保存，后者立即进行 JSON 文件写入、备份替换和 PlayerPrefs.Save。音量即时生效，但改为松手/关闭窗口/短暂防抖后落盘；暂停时仍保存。任务关键进度的低频即时保存可以保留。
2. FarmingPuzzle.GetCurrentHint 每帧 new[] {whitePen, blackPen}；缓存数组或直接处理两头牛，避免持续小分配。缓存每帧重复取得的 NPC/Collider/SpriteRenderer。
3. LevelBase 与 DialogueUI 打字机用 text += char，产生临时字符串并让 UI 更新。现阶段一句话不是主要瓶颈，后续可用 TMP 的 maxVisibleCharacters；动态文字/头顶标签/动画和静态大面板分 Canvas，减少整块界面反复重建。
4. 牛 AI 当前仅两只，且使用了缓冲数组和逃跑状态门控，是可保留的设计。每次逃跑更新仍有 16 个方向加补充检测、最多 80 次瞬移候选；后续若增加几十个动物，要限制活动距离、降低决策频率而保留物理移动频率。OverlapCircleAll 的分配只在特定可选脱困分支，不应误判为当前必定每帧调用。
5. URP 开启 HDR、Render Scale=1，后处理未启用、MSAA=1。先复制手机专用质量档，对比关闭 HDR 和按设备降低渲染分辨率；不要仅因为配置写着阴影就断言有大量阴影绘制，2D 灯光/相机实际效果要看 Frame Debugger/Profiler。未发现生产代码设置目标帧率；建议先稳定 30fps，再选择性提供 60fps。
6. 当前音频库只有 2 个短音效，尚非主要压力；日志播放开关开启。正式版本关闭高频播放日志。以后不要把五关长 BGM 全部通过常驻音频库强引用并解压，长音乐采用流式/按需加载，短音效按延迟需求设置。
7. 现有 VideoClipImporter 配置出现 customWidth=3840、customHeight=2160，实际导出是否采用此尺寸还受 resizeFormat/平台设置影响，需在 Unity 检查导入后视频参数。手机过场先以 720p/1080p 对照，不直接沿用潜在 4K 转码。1024×1024 RenderTexture 有深度缓冲，若只是 UI 视频显示可评估按视频比例创建无深度缓冲的 RenderTexture，并验证颜色与缩放。
8. 字体源文件约几十 MB，3 个较大字体合计约 39 MiB；不是持续帧率的首要原因，但需要检查打包保留范围、字体合规使用与中文字符覆盖。TMP Examples & Extras 内有 Resources，示例资源可能随包保留；确认没有依赖再清理示例内容，勿删除 TMP 必需 Resources。

## Android 构建与验证

现有 AndroidTargetArchitectures=1，为 ARMv7 配置，且 scriptingBackend 没有显式 Android 项。正式发布前设置并验证 IL2CPP + ARM64，必要时兼容 ARMv7；这不是单独的防卡按钮，但应尽早打出目标架构包。最低 SDK 目前 22、目标 SDK 自动，发布时按渠道当前要求配置，不把低最低 SDK 当作已适配低端机。

建议选一台计划支持的较低配置手机、一台主流手机。先用 Development Build 配合 Profiler 定位，再用接近发布的包复测；诊断包有额外开销。30fps 对应每帧约 33.3ms，60fps 对应约 16.7ms。不要只看平均 FPS；看 CPU/GPU 帧时间、长帧、内存峰值、GC 分配、UI 重建和加载时间。

回归流程：冷启动 → Logo → 菜单 → 选关 → 每个页面来回切 → 播砖画 → 进第一关 → 跑动/赶牛/对话/拼图 → 返回选关，循环 10 次；再连续玩 15～20 分钟看发热与降频。锁屏/切后台/系统回收后恢复，检查存档、音频、输入锁。记录进入前后和返回后的内存，不把系统分配器缓存直接认作泄漏。当前 SaveManager 已有 OnApplicationPause 存档和备份保护，可保留并真机验证。

初始验收要求：目标低配机达到选择的帧率档，日常交互无明显长帧，常态玩法尽量接近零持续 GC 分配；关卡往返内存不持续上涨；任何进度保存后可从后台恢复。不要给所有安卓机承诺一个统一的“安全内存 MB 数”，以实测 PSS/Unity 原生与图形内存、最低支持机余量来设项目预算。

## 实施顺序

1. 建可回退版本，先记录当前安卓第一关基线。
2. 精简 Select 依赖，统一异步进关/退关流程。
3. 用 Logo 和一组砖画试做视频/轻量效果/压缩对照；确认事件和美术效果后再批量处理。
4. 精简第一关角色控制器，设置安卓纹理规格，修正缺失引用。
5. 完成触屏、安全区和音量保存节流，建立手机质量档。
6. 跑通安卓完整第一关，再把该规范复制到后面四关。

附件：resource-audit.json 为当前资源/依赖快照；all-animations.csv 列出全部现存动画、时长、采样率、引用纹理数和事件。后续素材变动会使清单过时，需要重新采集。
